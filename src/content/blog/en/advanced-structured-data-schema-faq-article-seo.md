In a [previous guide](/en/blog/schema-markup-json-ld-astro-seo-italy/), we saw how to set up the basics of Structured Data (JSON-LD) on an Astro project to define brand identity and local SEO. However, if you want to literally "steal" visual space from your competitors on Google's search results pages (SERPs), you need to take it a step further.

Google rewards well-structured content by displaying **Rich Snippets**: interactive blocks, drop-down menus, and step-by-step guides that appear directly in search results. Securing these snippets massively increases your Click-Through Rate (CTR).

Let's see how to implement the three most powerful advanced schemas for corporate content marketing in Astro: `FAQPage`, `HowTo`, and the advanced version of `Article` - and where, on my own site, I made different choices than the "textbook" ones, for a good reason.

### 1. "FAQPage" Schema (The Space Stealer)
If you have a services page or an article with a "Frequently Asked Questions" section, the `FAQPage` schema is mandatory. This schema allows Google to display your questions and answers in a drop-down accordion directly below your link in the SERP, pushing competitors further down the page.

Here is how to generate it dynamically in an Astro component (e.g., `FaqSection.astro`):

```astro
---
const faqs = [
  {
    question: "How much does an Astro website cost?",
    answer: "The cost varies based on complexity and business integrations, but a basic project usually starts at €3,000 to ensure performance and security."
  },
  {
    question: "Is Astro better than WordPress?",
    answer: "For corporate sites, blogs, and landing pages, Astro offers significantly higher performance and zero vulnerabilities related to WordPress plugins."
  }
];

const faqSchema = {
  "@context": "https://schema.org",
  "@type": "FAQPage",
  "mainEntity": faqs.map(faq => ({
    "@type": "Question",
    "name": faq.question,
    "acceptedAnswer": {
      "@type": "Answer",
      "text": faq.answer
    }
  }))
};
---

<!-- JSON-LD Injection -->
<script type="application/ld+json" set:html={JSON.stringify(faqSchema)} />

<!-- Visual HTML Rendering -->
<section class="faq-container">
  <h2>Frequently Asked Questions</h2>
  {faqs.map(faq => (
    <details>
      <summary>{faq.question}</summary>
      <p>{faq.answer}</p>
    </details>
  ))}
</section>
```

This pattern already exists on my site, with one extra detail: each article's `faqs` frontmatter field (validated with Zod, as I cover in my [guide to Content Collections](/en/blog/astro-content-collections-zod-multilingual-blog/)) feeds both the visual `<FAQ>` component and its `FAQPage` JSON-LD, generated by that same reusable component for every post - no schema hand-duplicated page by page.

### 2. "HowTo" Schema (For Guides and Tutorials)
If you write tutorials (e.g., "How to configure a server" or "How to change a car tire"), the `HowTo` schema tells Google that your content is a sequential procedure. This can help you appear with special snippets displaying the various steps, required time, and even the necessary tools.

```astro
---
const howToSchema = {
  "@context": "https://schema.org",
  "@type": "HowTo",
  "name": "How to optimize images in Astro",
  "description": "A step-by-step guide to implementing the native <Image/> component and serving WebP/AVIF formats.",
  "totalTime": "PT15M",
  "tool": [
    { "@type": "HowToTool", "name": "Astro Framework" },
    { "@type": "HowToTool", "name": "Node.js" }
  ],
  "step": [
    {
      "@type": "HowToStep",
      "name": "Import the Image component",
      "text": "Add the import string at the top of the frontmatter: import { Image } from 'astro:assets';",
      "url": "https://yoursite.com/guide#step-1"
    },
    {
      "@type": "HowToStep",
      "name": "Replace the img tag",
      "text": "Replace old HTML tags with the Astro component to enable automatic optimization.",
      "url": "https://yoursite.com/guide#step-2"
    }
  ]
};
---
<script type="application/ld+json" set:html={JSON.stringify(howToSchema)} />
```

An honest note: I don't use `HowTo` on my blog yet, because none of my articles are structured as a numbered checklist of steps with a tool and an estimated time - they're discursive guides, not procedures. I'd only introduce this schema on content genuinely written in that form: a schema that promises "steps" but links to a continuous wall of text risks being penalized rather than rewarded.

### 3. Advanced "Article" Schema (E-E-A-T Optimization)
The basic `Article` markup (title, image, date) is no longer enough for sensitive topics (finance, health, advanced tech). Google's algorithm rewards E-E-A-T (Experience, Expertise, Authoritativeness, Trustworthiness).

To demonstrate authority, we must expand the `author` object by providing external links that certify who we are, and add the `publisher` object to tie the article to the corporate brand. One direct, "textbook" approach is to inline this data in full on every page:

```astro
---
const { title, description, pubDate, updatedDate } = Astro.props;

const basicArticleSchema = {
  "@context": "https://schema.org",
  "@type": "Article",
  "headline": title,
  "description": description,
  "datePublished": new Date(pubDate).toISOString(),
  "dateModified": updatedDate ? new Date(updatedDate).toISOString() : new Date(pubDate).toISOString(),
  "author": {
    "@type": "Person",
    "name": "Jane Doe",
    "url": "https://yoursite.com/about",
    "sameAs": [
      "https://linkedin.com/in/your-profile",
      "https://github.com/your-profile"
    ]
  },
  "publisher": {
    "@type": "Organization",
    "name": "Your Company Name",
    "logo": {
      "@type": "ImageObject",
      "url": "https://yoursite.com/logo.png"
    }
  }
};
---
<script type="application/ld+json" set:html={JSON.stringify(basicArticleSchema)} />
```

It works, but it has a flaw: publish a hundred articles and you repeat the same name, the same social links, the same logo a hundred times - identical data copy-pasted page after page. On my site I use a different pattern: I define the `Person` and `Organization` entities **once**, in a shared `@graph` in the main layout's `<head>`, each with a stable `@id` (`#person`, `#organization`), and every article simply *references* them:

```typescript
// In the shared layout (once per page)
"author": { "@id": SCHEMA_IDS.person },       // -> https://www.leonardocastignani.it/#person
"publisher": { "@id": SCHEMA_IDS.organization }, // -> https://www.leonardocastignani.it/#organization
```

The benefit isn't just avoiding repetition: when I update a social link or the company logo, I change it in exactly one place and it propagates automatically to every past and future article, instead of having to regenerate the schema on a hundred pages. For the same reason I use `BlogPosting` (a subclass of `Article` built specifically for blog posts) instead of the generic `Article`, and not `TechArticle`: that category is meant for highly specialized technical documentation, not for in-depth articles like this one.

Building an elegant interface is only half the job of a modern developer. Providing search engines and Artificial Intelligences with a structured, unambiguous machine vocabulary is what transforms a "pretty site" into a marketing asset capable of generating qualified traffic and business leads - the same quotability principle I cover in my [guide to GEO](/en/blog/geo-generative-engine-optimization-ai-search-italy/).
